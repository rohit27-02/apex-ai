# Plan: POC Bug Audit & Fix

The backend (orchestrator, handlers, runners, API) and frontend (canvas, inspector, console) are already very complete. This plan fixes the concrete bugs and gaps found during audit.

---

## Bug 1: Zod validation strips tokenUsage/durationMs

**Problem:** `validation.ts` `NodeRunStateSchema` doesn't include `tokenUsage` or `durationMs`. `RunSchema` doesn't include `totalTokenUsage` or `totalDurationMs`. Zod strips these fields on parse, so the node detail popup never shows stats.

**Fix in `src/lib/validation.ts`:**
- Add `TokenUsageSchema`
- Add `tokenUsage` and `durationMs` to `NodeRunStateSchema`
- Add `totalTokenUsage` and `totalDurationMs` to `RunSchema`

---

## Bug 2: Backend adapter doesn't map stats

**Problem:** `backend-adapter.ts` `backendRunToRun()` doesn't map `tokenUsage`/`durationMs` from the backend. The backend tracks `cost.model_calls` and `cost.seconds` at the run level, and `started_at`/`ended_at` per node.

**Fix in `src/lib/backend-adapter.ts`:**
- Compute `durationMs` from `started_at` and `ended_at` for each node
- Map `cost.model_calls` and `cost.seconds` to `totalTokenUsage`/`totalDurationMs` on the Run (best-effort; the backend doesn't have per-token counts, so use model_calls as a proxy)

---

## Bug 3: Canvas page sync doesn't pass duration/stats to node data

**Problem:** `canvas/page.tsx` sync sets `status`, `output`, `error`, `logs`, `criteria` on node data but NOT `durationMs` or `tokenUsage`. The node detail popup references these but they're always undefined from real runs.

**Fix in `src/app/canvas/page.tsx`:**
- Add `durationMs: nodeState?.durationMs ?? null` and `tokenUsage: nodeState?.tokenUsage ?? null` to the node data sync

---

## Bug 4: use-run-sync hook is unused dead code

**Problem:** `hooks/use-run-sync.ts` defines a sync hook but `canvas/page.tsx` has its own inline sync logic. The hook is dead code.

**Fix:** Remove `hooks/use-run-sync.ts` — the inline sync in `canvas/page.tsx` is more complete (it handles criteria, output, error, logs). The hook only syncs status.

---

## Bug 5: Settings model doesn't propagate to agent dropdown

**Problem:** The settings modal has a free-text model input. If the user types a custom model there, the agent-fields dropdown (which only shows `PROVIDER_MODEL_OPTIONS[provider]`) won't include it. The `agent-fields.tsx` has logic to keep an out-of-list value visible, but only if it was previously set on the node — it won't appear in the dropdown options list.

**Fix in `src/components/inspector/fields/agent-fields.tsx`:**
- Also include `useSettingsStore().model` (the global model from settings) in the dropdown options if it's not already in the provider's list

---

## Bug 6: No workflow persistence

**Problem:** Workflow is only in memory (Zustand). Refreshing the page resets to default.

**Fix in `src/stores/workflow-store.ts`:**
- Use Zustand `persist` middleware to save workflow to localStorage
- Add `loadWorkflow` / `saveWorkflow` actions

---

## Bug 7: No workflow import

**Problem:** Export exists but no import. Track B requires "Importing and rerunning the same configuration is desirable."

**Fix in `src/components/topbar/export-button.tsx`:**
- Add an Import button next to Export
- Use a file input to read a JSON file, parse it as a Workflow, and call `setWorkflow()`

---

## Bug 8: CriteriaReview not wired into run flow

**Problem:** `CriteriaReview` component exists but isn't shown anywhere in the run flow. Track B requires "Before execution, the engineer should be able to review, edit, prioritize, and confirm the criteria."

**Fix in `src/app/canvas/page.tsx`:**
- After the first agent (criteria) completes and before the rest of the loop continues, show the CriteriaReview in the inspector panel
- This is already partially handled by the backend (criteria are seeded from config), but the UI should show them for review

Actually — the backend handles criteria synchronously in the agent handler (seeded from config or generated). The criteria review should happen in the UI BEFORE the run starts, not during. The current flow is: user clicks Run → objective dialog → run starts immediately.

**Better fix:** Add a criteria confirmation step in the Run dialog. After entering the objective, show the criteria from the input node's config for review/edit before starting the run. This keeps the backend flow unchanged.
